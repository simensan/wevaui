# Core JPEG decoding — 2026-11-01

Weva now decodes baseline and progressive JPEG in its C++ core, including grayscale
and CMYK. Dispatch uses encoded bytes, so a JPEG named `.png` works. No host-side
conversion, PNG behavior change or C ABI change is involved. The decoder checks
encoded dimensions before allocation and retains the PNG path's 64-megapixel ceiling.

The dependency is unmodified `stb_image.h` at upstream commit
`013ac3beddff3dbffafd5177e7972067cd2b5083`, compiled with only JPEG enabled and no stdio.
Source: https://github.com/nothings/stb/tree/013ac3beddff3dbffafd5177e7972067cd2b5083
SHA-256: `594c2fe35d49488b4382dbfaec8f98366defca819d916ac95becf3e75f4200b3`.
Its dual MIT/public-domain license is retained and included in native SDK packaging.
Consumers that validate exact SDK license inventories need to admit `stb.txt` when
adopting this version. This is not an Agentic SDK adoption or cross-platform release.

## Evidence

Before the change, a fresh four-image software render produced **zero textures**
and named all four JPEG fixtures as failures. After the change, the native tests
pass exact pixel expectations independently established using pinned Chrome
152.0.7977.82: baseline/progressive RGB `(64,128,192,255)`, grayscale
`(96,96,96,255)`, CMYK `(167,111,55,255)`, each 16x8 and uniform. No tolerance was
widened. The regression matrix also covers cached extension-independent reads,
async progressive decoding, truncated headers, null/oversized input and dimensions
above the pixel budget. Existing PNG/filter/cache cases continue to pass.

The actual host-game source icons `ThunderStrike.jpg` and `ToxicCanister.png`
(the latter is JPEG) now produce two textures in `weva_render`. This output was
